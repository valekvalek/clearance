## Сводка за 20.10.2026

Коротко, что сделано за день (подробности — в одноимённых разделах ниже,
в хронологическом порядке):

1. **Миграция основного ИИ-провайдера на Yandex Cloud AI Studio** — вместо
   Gemini, с резервным переключением обратно через один env (`AI_PROVIDER`).

   **Yandex Search API «Картинки»** — рабочий и надёжный вариант.
3. **Деплой на боевой VPS** (Aeza) + домен (DuckDNS) + настоящий HTTPS
   (Let's Encrypt) — сервис доступен по ссылке.
4. **Демо-доступ** с лимитом в 5 обработок и окном «нужна подписка» после.
5. **Закупка (Китай)** — разобрались в текущем функционале, решили пока не
   подключать платный Oxylabs.
6. **Кнопка «Шаблон ТЗ»** во вкладке «Закупка» — готовый xlsx-шаблон с
   инструкцией, что писать, чтобы программа нашла нужные товары.
7. **Веб-поиск (и фото) в «Закупке» — теперь всегда включён**, без
   чекбокса (принудительно на сервере, не только спрятан в интерфейсе).
8. **Удаление из истории** («✕» на карточке результата и в списке) — только
   для своих файлов.
9. **Проверка ссылок-поисков на площадках в браузере** — нашлись и
   исправлены 2 реальных бага (1688 — кодировка GBK, Made-in-China —
   устаревший URL).
10. **Гиперссылки в экспортируемом xlsx** — ссылка на товар и ссылка в
    описании теперь кликабельны прямо в Excel.
11. **Замер расхода токенов/рублей**, попытка сэкономить на модели
    (yandexgpt-lite — эффект ограничен лимитом параллельных запросов),
    **кеш повторяющихся запросов/фото** (90 дней) и **Яндекс.Диск как
    хранилище** результатов и кеша фото (вместо диска сервера).

## Как продолжить

Скажите Claude в этой папке:

> Прочитай `docs/ПЛАН_ДОРАБОТКИ.md` и продолжи доработку со следующего шага.

**Порядок работы, о котором договорились:**
1. Перед каждым шагом Claude пишет, что будет делать, и ждёт «да».
2. После шага Claude отчитывается: что изменено, в каких файлах, как проверено. Затем предлагает следующий шаг.
3. Каждую правку нужно проверить тестами. Если задет интерфейс, Claude проверяет его ещё и в Chrome через расширение Claude in Chrome.
4. Реальную папку `data/` не трогать, все проверки делать на тестовых данных.
5. Ответы на русском.

**Контекст:**
- До 11.10.2026 приложение работало на VibeCode (Bitrix24) — временном хостинге с ИИ от Bitrix24. Теперь это в прошлом: хостинг — свой сервер, ИИ — Google AI Studio (Gemini, см. запись «Миграция VibeCode → Gemini» ниже). Всё по-прежнему без жёсткой привязки к конкретному хостингу: настройки через переменные окружения (`app/.env`).
- Ключ Gemini (`GEMINI_API_KEY`) — у пользователя, в `app/.env`. Без него обработку инвойсов проверяем на заглушке вместо реального ИИ.
- Git в папке проекта не используется, поэтому истории правок нет. Исходный код до всех правок лежит в `backup/app_original/`. Перед большими изменениями стоит сделать ещё одну копию `app/`.

просил Next.js/Tailwind — в проекте их нет и не заводили, сделали то же самое на чистом
HTML/CSS/JS, как и было). backend-код, docstring'и и README **не переименовывались** — так
попросил пользователь; переименование только в UI и в именах файлов результата.

**Что сделано:**

- **Тема**: light/dark на CSS-переменных (`:root` / `:root[data-theme="dark"]`), переключатель

**Важно для продолжения:**
- Тестовая инфраструктура (`tests/run_all.sh`, `tests/xss_18.js`, `tests/click_18.js`) жёстко

| 2.1 | **Потери товаров видны.** Упавший кусок большого файла, скан PDF и пачка перевода получают одну повторную попытку. Что не удалось, попадает в предупреждения: «Не распознаны строки R46–R90 (файл 1 «…», лист «…»)», «Файл не прочитан», «скан на 10 стр., распознаны первые 8», «лист обрезан после 3000 строк», «10 товаров без перевода (№ 101–110)», «поиск в интернете не сработал». | 2.4 | **Все суммы в долларах по курсу ЦБ РФ.** Источники по очереди: `cbr.ru` (XML), зеркало `cbr-xml-daily.ru`, последний курс с диска `DATA_DIR/rates.json` (с предупреждением). Неизвестная валюта или нет курса: ячейка $ пустая плюс предупреждение. Строка курса в интерфейсе: «ЦБ РФ на ДАТА: 1 USD = 6.71 CNY · …» | `currency.py` (переписан), `pipeline.py` (`usd()`), `jobs.py`, `index.html` |
| 2.5 | **Числа из инвойса.** Новая `_parse_amount()` (используется в `_num()`): срезает валюту и любые пробелы (в т.ч. неразрывные), сама определяет десятичный разделитель и разделитель тысяч — `12,5`→12.5, `1,234`→1234, `1.234,56`→1234.56, `1,234.56`→1234.56, `1 234,56` (неразрывный пробел)→1234.56, `¥12.5`/`12.5 USD`/`€5` разбираются с извлечением валюты. Если поле валюты в инвойсе пустое, используется валюта, найденная прямо в ячейке цены (явно указанная валюта не перебивается). Если `total_price` или `unit_price` отсутствует, он досчитывается из другого (`qty × unit_price` / `total_price / qty`). Цена без единой цифры («по запросу» и т.п.) не считается легитимным нулём: попадает в предупреждения — «Товар № N: цена «…» не распознана» (легитимный `0` не помечается) | `pipeline.py` (`_parse_amount`, `_num`, `_items_from_json`, `extract_all`) |
| 2.2 | **Крупные файлы режутся по листам.** Раньше кусок для ИИ вырезался произвольным окном (45 строк) прямо из текста, где подряд склеены ВСЕ листы/файлы — окно могло оборваться посреди листа и захватить хвост соседнего, а «шапкой-контекстом» для любого куска служили первые строки всего документа, а не того листа, к которому кусок относится. Теперь режем каждый лист отдельно: у каждого куска свой маркер «ФАЙЛ N · ЛИСТ» и своя шапка (первые строки именно этого листа). Раз инвойс и пакинг-лист крупного файла почти всегда попадают в разные куски, инструкция ИИ «объедини их» внутри куска уже не работает — добавлено сведение **в коде** после распознавания (`_merge_invoice_packing`): товары без сопоставления сравниваются по артикулу, затем по внутреннему коду, затем по наименованию (без учёта регистра); у найденной пары вес переносится в запись с ценой, а запись-дубль без цены убирается — порядок и номера остальных товаров (важно для «Товар № N» в предупреждениях) не меняются. Убранная строка пакинг-листа запоминается в `src_alt`: если фото не нашлось у главной строки товара, `map_source_images` пробует строку из `src_alt` — так фото не теряется, если оно оказалось не в той строке, что цена. `src_file`/`src_sheet` для куска теперь проставляются самим кодом (мы точно знаем, откуда вырезан кусок), а не берутся из самоотчёта ИИ — иначе пустое/неточное поле «sheet» в ответе ломает дедуп по позиции (см. 2.3) | `pipeline.py` (`extract_items`, `_merge_key`, `_merge_invoice_packing`, `map_source_images`, `_map_alt_images`); убраны `_MARKER_RE`, `_describe_lines` (не нужны при нарезке по листам) |
| 2.3 | **Дедуп по позиции, а не по содержимому.** Раньше две ОДИНАКОВЫЕ, но законные строки (тот же товар в двух разных заказах по той же цене) склеивались в одну. попадает (`.dockerignore`) — для контейнера передавайте переменные через `-e` или монтируйте
`.env` отдельным томом.

**Новые переменные окружения** (все необязательные):
- `ALLOWED_ORIGINS` — свой домен после переезда, например `https://invix.example.com`;

- `JOB_WORKERS` (3) — сколько задач обрабатывается одновременно, остальные ждут в очереди;
- `GEMINI_MAX_CONCURRENT` (10) — общий лимит одновременных запросов к Gemini на весь процесс;
- `JOB_TIME_LIMIT` (1800, сек) — общий бюджет времени на одну задачу, после — ошибка вместо зависания.

**Новые файлы в `DATA_DIR`:** `app.db` (SQLite — пользователи/сессии/статистика/активность, шаг 3.5), `rates.json`, `jobs.json`. Если не задан `ADMIN_PASSWORD`, ещё `initial_admin_password.txt`. **Новые модули** (попадают в образ через `COPY . .`): `uploads.py`, `guards.py`, `report.py`, `jobs.py`.

## Миграция VibeCode → Google AI Studio (Gemini), 11.10.2026

Пользователь: «битрикса больше нет и не будет, API-ключ будет от гугл студии, убери всё, что
связано с Bitrix». Повод — ключ, вписанный в `app/.env` для VibeCode, на самом деле оказался
не того формата (`AQ.Ab8RN...`, а не `vibe_api_...`, см. запись выше) и в процессе выяснилось,
что VibeCode/Bitrix24 вообще не будет использоваться дальше.

**Что сделано:**
- `app/vibecode.py` удалён, вместо него новый `app/gemini.py` — тот же внешний интерфейс
  (`chat`, `chat_vision`, `search`, `extract_json`, `API_KEY`, `MODEL`), но внутри вызывает
  Google AI Studio (`generativelanguage.googleapis.com/v1beta/models/{model}:generateContent`)
  вместо VibeCode. Авторизация — заголовок `x-goog-api-key` (не `Authorization`/`X-Api-Key`,
  у Google своя схема). `messages` (OpenAI-формат: system/user) конвертируются в Gemini-формат
  (`systemInstruction` + `contents`) — у нас везде ровно одна системная и одна пользовательская
  реплика без истории диалога, поэтому конвертация простая (не тащили полноценный chat-формат).
  `chat_vision` — картинки передаются как `inline_data` (base64 PNG) рядом с текстом в тех же
  `contents`, как и раньше с VibeCode.
- **Веб-поиск** (функция «искать ссылки/материал в интернете», галочка в интерфейсе) раньше шёл
  через отдельный `vibecode.search(query)` → `{answer, results[]}`. У Google AI Studio
  отдельного поискового API нет — поиск встроен в саму модель через
  `tools: [{"google_search": {}}]` на `generateContent`. Новый `gemini.search()` сохраняет ТОТ
  ЖЕ интерфейс (`{answer, results:[{url,title,content}]}`), чтобы `enrich.py` не пришлось
  переписывать — только `content` у результатов теперь всегда пустой: `groundingChunks` в
  ответе Gemini дают только заголовок и ссылку, без сниппета страницы (сама выжимка — в
  `answer`, она и так используется отдельно в промпте `enrich.py`, см. `_enrich_one_batch`).
  Пользователь подтвердил этот вариант (не отключать поиск) — учитывайте, что при включённой
  галочке «искать в интернете» каждый запрос с поиском у Google AI Studio тарифицируется
  отдельно от обычных запросов (платный grounding), дороже чем генерация без поиска.
- Модель по умолчанию — `gemini-2.5-flash` (выбор пользователя из предложенных вариантов:
  2.5-flash/2.5-pro/2.0-flash — flash как баланс скорости/цены/качества, ближайший аналог
  прежней `bitrix/bitrixgpt-5.5`). Переопределяется как и раньше через `AI_MODEL`/`EXTRACT_MODEL`.
- Переменные окружения: `VIBE_API_KEY` → `GEMINI_API_KEY`, `VIBE_MAX_CONCURRENT` →
  `GEMINI_MAX_CONCURRENT`. Убраны `VIBE_BASE_URL`/`VIBE_SEARCH_URL`/`VIBE_SEARCH_PROVIDER` (не
  нужны — у Gemini фиксированный `v1beta` эндпоинт, поиск встроен, провайдер не выбирается);

## Фото из веб-поиска, когда нет своего фото в файле (20.10.2026)

Пользователь протестировал реальный Yandex-прогон и решил, что хотел увидеть:

загруженных файлов»). Выбрал вариант: брать фото с ЛЮБЫХ сайтов из
результатов веб-поиска (не только китайских площадок).

**Попутно найден и исправлен реальный баг** в `images._map_excel_images()`
(привязка фото из xlsx по строке-якорю): если у двух товаров строки были
рядом (в пределах ±2), ОДНА картинка приклеивалась к ОБОИМ — функция не
помечала картинку «использованной» после привязки (в отличие от PDF-версии
той же логики, где такая пометка уже была). Теперь товары сортируются по
качеству совпадения и картинка, привязанная к одному, больше не достаётся
другому.

**Реализовано** (`enrich.py`): `_fetch_web_photos()` — для товаров без
`src_image` (ни из файла, ни от предыдущего шага) пробует взять фото со
страниц из результатов веб-поиска, которые УЖЕ получены для перевода/
описания (без повторных запросов/трат). Логика: открыть страницу → найти
`og:image` (или первый `<img>`, не похожий на иконку/логотип/спейсер по
имени файла) → скачать картинку → проверить, что это реально декодируемое
изображение разумного размера (`min(w,h) >= 100`, та же проверка, что у
файловых картинок в `images.py`). Любая проблема (сеть, 403/401/редирект,
нет og:image, картинка слишком мала) — тихо `None`, пробуется следующая
ссылка из топ-3 результатов, иначе товар остаётся без фото (как раньше).
Вызывается только при включённом чекбоксе «Искать... в интернете» — его
подпись в `index.html` обновлена (раньше явно обещала «фото — только из

## Фото: переход со скрапинга страниц на Yandex Search API «Картинки» (20.10.2026)

Пользователь, увидев первую версию (поиск фото через парсинг og:image со
страниц из текстового web_search — см. запись выше), предложил проще и
надёжнее: «поиск фото просто через поисковик Яндекса в разделе картинки».
Оказалось, у Yandex Cloud есть ОТДЕЛЬНЫЙ продукт **Search API** с методом
`ImageSearch` (`POST https://searchapi.api.cloud.yandex.net/v2/image/search`)
— это не часть Foundation Models/AI Studio (другой хост), но та же пара
ключ+folder заработала на нём без доп. включения в консоли (проверено
реальным запросом).

**Что сделано:**
- `yandex.py`: новая `image_search(query, count=5)` — вызывает `ImageSearch`,
  ответ приходит как `{"rawData": "<base64 XML>"}` (классический формат
  Яндекс.XML); декодирует и парсит через `xml.etree.ElementTree`, достаёт из
  каждого `<image-properties>` прямую ссылку `image-link` + размеры
  (`original-width/height`). Пустой список при любой проблеме (как и
  `search()`), не роняет обработку.
- `gemini.py`: `image_search()` — заглушка (пустой список), т.к. у Google
  AI Studio эквивалента нет; нужна только для того, чтобы диспетчер
  `ai_client` не падал при `AI_PROVIDER=gemini` (тестовый дефолт).
- `enrich.py`: `_fetch_web_photos()` переписана — вместо скачивания HTML
  страниц из текстового веб-поиска и парсинга `og:image`/`<img>` (весь этот
  код удалён: `_http_get`, `_extract_page_image_url`, `_fetch_image_from_page`,
  `_BAD_IMG_HINTS`, импорты `re`/`urljoin`) теперь просто зовёт
  `ai_client.image_search(_search_query(item))` и скачивает первую ссылку,
  которая реально декодируется. Отдельный от текстового поиска запрос — у
  Yandex это разные продукты с разным форматом, повторно использовать
  результаты `search()` для картинок было нельзя.

**Проверено реальным ключом пользователя:**
- Прямой вызов `image_search("kitchen electronic scale")` — вернул реальные
  ссылки на фото (ozon, alibaba и т.п.) с размерами, например `(800, 600)`.
- `enrich._fetch_web_photos()` на 2 тестовых товарах без своего фото —
  **2 из 2** нашли и скачали фото (800×600 и 800×1200) — заметно надёжнее
  прежнего подхода через скрапинг (там крупные магазины блокировали запросы).
- Полный цикл через реальный `/api/process` (форма `web=true` — поле
  называется `web`, не `web_search`, см. `app.py`) на эталонном
  `tests/fixtures/sample_invoice.xlsx` (в нём нет своих фото) — **все 3
  товара получили фото** из интернета, предупреждение «Фото из интернета
  (Яндекс.Картинки) подставлено для 3 товар(ов)» корректно показано в
  превью и в итоговом xlsx.
- `pytest tests/` — 24 passed после замены (старая запись выше про скрапинг
  страниц устарела в части реализации, но её анализ блокировок крупных
  магазинов остаётся верным наблюдением о подходе «открыть страницу и
  вытащить og:image» — именно поэтому от него и отказались).

**Важно для продолжения:**
- `SEARCH_TYPE_COM` (коммерческий поиск) — предположение по примеру из
  документации; если качество найденных фото/релевантность окажется низкой
  на реальных инвойсах, стоит свериться со списком допустимых значений
  `searchType` в документации Yandex Search API — другие варианты не
  проверялись.
- Этот сервис (`Search API`) — отдельный от Foundation Models продукт
  Yandex Cloud; биллинг/лимиты у него могут отличаться (не проверялось) —
  стоит иметь в виду при реальной нагрузке.
- `familyMode: FAMILY_MODE_MODERATE` — фильтр взрослого контента, оставлен
  включённым по умолчанию, трогать не было причины.

Проверял вручную (Claude in Chrome) на реальном запросе («三相异步电动机(带制动器)
YEJ2-132M-4» — электродвигатель из прошлых тестов).

**Найдено и исправлено в `sourcing.py` (`deep_links()` и `source_via_oxylabs()`):**
- **1688 — реальный баг.** Параметр `keywords` нужно кодировать в **GBK**, а
  не UTF-8 (которую кодировал `quote()` по умолчанию). С UTF-8 сервер 1688
  показывал кракозябры в заголовке страницы, а результаты поиска были
  вообще не по теме (случайные украшения вместо электродвигателей) —
  классический симптом, когда сервер декодирует UTF-8-байты как GBK.
  Исправлено: `quote(kw.encode("gbk", errors="ignore"))`. Проверено: после
  исправления результаты точно по теме (первая же карточка — нужная модель
  двигателя).
- **Made-in-China — реальный баг.** Старая ссылка
  `/productdirectory.do?word=...` отдавала «The information you are looking
  for is not available currently» — эндпоинт сам по себе рабочий, но без
  параметра `subaction=hunt` не ищет (подсмотрено из реальной формы поиска
  на сайте, протестировано вручную). Добавлен `subaction=hunt` в URL.
  Проверено: 17 точных результатов по модели.
- Тот же GBK-баг был и во втором месте с тем же URL — `source_via_oxylabs()`
  (путь, который используется, если когда-нибудь подключат платный
  Oxylabs) — поправлено для консистентности, хотя не проверялось отдельно
  (Oxylabs не подключён, см. запись выше про решение не подключать).

**НЕ баг, но важное ограничение площадок (ничего не меняли, т.к. не в
коде):**
- **Taobao и Tmall** (Tmall редиректит на тот же Taobao) — кодировка (UTF-8)
  в порядке, сам эндпоинт рабочий, НО площадка требует быть залогиненным в
  аккаунт Taobao в браузере — без входа вместо результатов показывает

  быть залогиненным в Taobao в своём браузере, чтобы эти 2 ссылки из 5
  показывали результаты.
- **Alibaba.com** — работала отлично без изменений: UTF-8, без входа,
  1000+ релевантных результатов.

**Итог по всем 5 площадкам после исправлений:** 1688 ✅ (исправлено),

## Замер расхода токенов/рублей + кеш запросов + Яндекс.Диск как хранилище (20.10.2026)

Пользователь попросил измерить реальный расход токенов и денег на обработку,
и после этого — пути сокращения расходов при нагрузке 10–20 больших файлов
в день.

**Замер токенов:** добавлено логирование расхода токенов в `yandex.py`
(`_log_usage`, вызывается из `chat`/`chat_vision`/`search`) + накопительный
счётчик в памяти процесса (`yandex._TOKENS_TOTAL`) + админ-эндпоинт
`GET /api/admin/token-usage`. Сброс только при перезапуске контейнера —
не персистентная статистика, для разовых замеров достаточно.

**Расчёт в рублях** (по публичному прайсу Yandex Cloud на 20.10.2026,
точное соответствие `yandexgpt/latest`/`yandexgpt-lite/latest` конкретным
тарифным строкам не подтверждено официально — см. предупреждение в самом
расчёте, для точных цифр пользователю стоит смотреть детализацию в своём
личном кабинете): маленький файл (3 товара, без веб-поиска) — ≈3,6 ₽;
большой файл (69 товаров, с веб-поиском и поиском фото) — ≈206–216 ₽, из
которых **~70% — веб-поиск и поиск фото**, не сам перевод.

**Модель на yandexgpt-lite:** переключили `AI_MODEL=yandexgpt-lite/latest`
(4x дешевле токен), с фоллбеком на полную `yandexgpt/latest` при лимитах
(`YANDEX_MODEL_FALLBACKS=yandexgpt/latest,yandexgpt-lite/latest`). Качество
перевода на тестовом файле не отличалось от полной модели. **Важная
находка**: у Lite свой лимит на ~5 одновременных запросов, а перевод
параллелит 6 (`batch_workers=6`) — на больших файлах Lite почти сразу
упирается в свой лимит и откатывается на дорогую модель для большей части
перевода, так что реальная экономия на больших файлах от одной только смены
модели оказалась минимальной/нулевой. Пользователь решил оставить как есть
(дёшево на маленьких файлах, автооткат на лимите — достаточно).

**Кеш веб-поиска и фото** (новый модуль `cache.py` + 2 таблицы в `db.py`:
`search_cache`, `photo_cache`) — ключ: тот же нормализованный запрос
(китайское название + артикул), что уже используется для поиска. TTL —
**`CACHE_TTL_DAYS=90`** (сначала поставили 7 по просьбе пользователя,
позже увеличили до 90 — места на Яндекс.Диске достаточно, не было смысла
обновлять кеш так часто). Подключено в `enrich.py`: и текстовый поиск
(`ai_client.search`), и поиск фото (`ai_client.image_search` +
`_download_image`) сначала проверяют кеш, пишут в него только успешные
результаты. Проверено: повторная обработка того же товара — **0 новых
запросов** на поиск/фото, полностью из кеша.

**Яндекс.Диск как хранилище** (новый модуль `yadisk.py`) — пользователь
спросил про облачное хранилище, обсудили, что переносить стоит только
большие редко читаемые файлы (готовые xlsx-результаты и кеш фото), а НЕ
живую SQLite-базу (частые быстрые запросы, HTTP-хранилище для этого не
подходит, риск гонок по сети). Используется scope `cloud_api:disk.app_folder`
(приложение видит только свою папку на Диске пользователя, не весь
остальной Диск) — токен получен пользователем через
`oauth.yandex.ru/authorize?response_type=token&client_id=...`, передан в
чат, сохранён в `.env` как `YADISK_TOKEN`.
- `activity.py` (`_store_result`/`read_result`/`delete_result`): если
  `YADISK_TOKEN` задан и загрузка прошла успешно — xlsx уходит на Диск,
  ЛОКАЛЬНО НЕ СОХРАНЯЕТСЯ (экономия диска сервера — ради этого всё и
  затевалось). Если Диск не настроен или загрузка не удалась — как раньше,
  локальный файл (полностью обратная совместимость, ничего не ломается без
  токена). В `index.json` каждая запись получила поле `store`
  (`"yadisk"`/`"local"`) — старые записи без этого поля трактуются как
  `local` (обратная совместимость).
- `cache.py` (`set_photo`/`get_photo`): та же логика для кеша фото — путь в
  БД с префиксом `yadisk:` означает «скачивать с Диска», иначе — обычный
  локальный путь.
- Диск создаёт только корневую папку приложения автоматически; вложенные
  папки (`results/<user>/`, `photo_cache/`) нужно создавать явно —
  обнаружено на практике (первая попытка загрузки упала `409 CONFLICT`),
  добавлена `_ensure_parent_dirs()` в `yadisk.py`.
- **Пойманная и исправленная гонка** (не связанная напрямую с Диском, но
  проявившаяся из-за него): `jobs.py` помечал задачу `status="done"`
  ДО вызова `activity.on_result(...)` — пока результат был только локальным
  файлом, запись была мгновенной и гонка была незаметна; с сетевой
  загрузкой на Яндекс.Диск (не мгновенной) лента «Недавние результаты»
  иногда не показывала только что обработанный файл, если открыть её сразу
  после завершения. Исправлено — `on_result` теперь вызывается ДО
  `set_job(status="done")`, так что клиент узнаёт о готовности, только
  когда результат уже реально записан в историю.
- Проверено полным циклом с настоящим токеном: файл реально лежит на Диске
  (не на сервере), содержимое при скачивании совпадает, удаление через
  кнопку «✕» в истории реально стирает файл с Диска.

**Важно для продолжения:**
- Расчёт стоимости в рублях — по ПУБЛИЧНОМУ прайсу, не по вашему реальному
  договорному тарифу (не подтверждён официально по именам моделей) — для
  точных цифр смотреть детализацию биллинга в консоли Yandex Cloud.
- Кеш не ограничивает рост диска никакой верхней планкой по размеру —
  только по времени (90 дней, увеличено с 7 — пользователь решил, что места
  на Яндекс.Диске достаточно). При очень большом объёме уникальной
  номенклатуры стоит иметь в виду.
- Яндекс.Диск есть бесплатный лимит места (обычно ~10 ГБ) — при большом
  объёме кешируемых фото стоит следить за свободным местом в самом
  Яндекс.Диске, не только на сервере.
